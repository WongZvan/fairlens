## 1. 背景、定位与目标

### 1.1 背景

客户方要求为即将面试的候选人（按批次组织）提供**简历在线修订与大模型评估**能力。系统由独立开发者长期维护，需以最小维护成本持续演进，并为客户方不同专业方向的细分垂类预留灵活的提示词扩展接口。

### 1.2 产品定位

**简历 ADE**：以 IDE 形态组织的简历工作台。核心理念是"像开发者在 IDE 里写代码一样，候选人在 ADE 里打磨简历"——AI 逐块修订内联呈现（类比 Copilot），评估结果以诊断面板呈现（类比 Problems 面板）。

| IDE 概念 | ADE 对应 |
|---|---|
| 文件资源管理器 | 左侧简历结构树（基本信息/教育/经历/项目/技能） |
| 编辑器 + Copilot | 中间 Tiptap 编辑区，块级 AI 内联 diff 建议，逐条采纳/拒绝 |
| Problems 诊断面板 | 右侧评估面板：逐维度得分 + 问题清单，点击跳转对应经历块 |
| 本地 git 快照 | 每次 AI 采纳自动存版本快照，可对比/回滚 |
| 命令面板 Ctrl+K | 全局动作（改写此块/量化成果/STAR 化/全篇评估） |

> 术语说明：用户口中的"逐行修改"在富文本编辑器中落地为**块（block）粒度**——一个经历条目或一条要点描述即为一个块。块是 AI 修订、评估定位、快照 diff 的统一最小单元。

### 1.3 v1 目标（In Scope）

1. 结构化简历编辑器：模板新建、分区块编辑、自动保存。
2. 内容导入：粘贴文本、拖入/打开 DOCX（mammoth）与 PDF（pdf.js）提取文本并结构化入库。
3. AI 块级修订：OpenAI 兼容多厂商（DeepSeek/Qwen/GLM/豆包/自定义），SSE 流式，内联 diff，采纳/拒绝/重新生成。
4. 多维评估：按垂类 rubric 打分，结构化报告，诊断面板 + 雷达图，问题项跳转定位。
5. 授权体系：Ed25519 离线签名密钥 + **授权租赁端点**（唯一极小服务端）——**一码一机绑定、同时生效设备数上限、可吊销可解绑**；双角色（内部开发者 / 普通授权用户）。
6. 提示词 SPI + Prompt Studio（内部开发者）：按垂类编辑、实时调试、导出签名包推送仓库，客户端热拉取验签。
7. 版本快照与对比回滚。
8. Windows 安装包分发 + Tauri 自动更新。

### 1.4 非目标（Out of Scope，v1 明确不做）

- 计算机垂类工作台（Monaco 代码编辑、题库训练）→ v2，仅预留 SPI。
- **任何常驻自维护服务器**（数据库实例、容器、运维面板）→ 不做。v1 唯一服务端是一个约 100 行的无状态 Serverless 函数（授权租赁端点，见 §4.5），随代码库走、免费额度内、零运维（决策记录：2026-10-22，因"一码一机 + 设备数上限"必须有共享状态而引入）。
- 机构 Key 统一网关、设备台账/使用报表 → 待客户明确提出再立项；届时经 `LicenseProvider` 接口缝隙扩展，架构不变（见 §2、附录 B）。
- 多人协作、云同步、简历内容上云（简历全文永不离开本机）。
- PDF 排版级导出（v1 用系统打印对话框另存 PDF）、在线 Web 版。

### 1.5 关键用户特征（已确认）

- 使用者大部分具备 GitHub 镜像与代理网络条件 → 更新与提示词包走 GitHub 被动分发；激活绑定走租赁端点（见 §4.5 的国内可达性说明）。
- 简历属敏感个人信息 → 全部解析、编辑、存储在本地完成。

```
┌───────▼──────────────────┐   ┌──▼────────────────────────────────────┐
│ GitHub（被动基础设施）     │   │ 授权租赁端点（唯一服务端，~100 行）      │

│ │   提示词包（版本化）     │   │  KV 同时充当吊销名单（见 §4.5）         │
│ └─ 可选 jsDelivr 镜像     │   └────────────────────────────────────────┘
└──────────────────────────┘
```

**数据边界铁律**：简历正文、评估报告、API Key 仅存于本机；应用对外流量只有三类——GitHub 只读拉取（提示词包、更新）、用户自有 Key 的 LLM 直连、租赁端点（只传激活码与设备指纹哈希，无任何简历数据与个人信息）。

**LicenseProvider 缝隙**（授权策略可替换，UI 与业务不感知）：

```ts
interface LicenseProvider {
  verify(input: { licenseKey: string }): Promise<
    | { ok: true; license: LicenseClaims }   // { code, role, batchId, exp, maxDevices }
    | { ok: false; reason: 'bad-signature' | 'expired' | 'revoked'
                         | 'slots-full' | 'lease-expired' }>
}
```

v1 提供实现 `LeaseProvider`（离线验签 + 在线租约）；端点长期不可达时的降级路径与未来 `SupabaseProvider`（审计台账版）见 §4.5 与附录 B。

### 2.1 分层职责

| 层 | 职责 | 禁止事项 |
|---|---|---|
| WebView UI | 全部交互、编辑器、AI 调用编排 | 不做系统 I/O |
| packages/core | 纯 TS 领域逻辑（可单测）：diff 应用、评估管道、验签+租约状态机、LLM 客户端、提示词合成 | 不依赖 DOM/Tauri API |
| packages/shared | zod Schema、DTO、协议类型（含 LicenseClaims、Lease、PromptPack） | 无逻辑 |
| packages/prompts | 内置兜底提示词包 + PromptPack 校验/合成器 | 不含业务逻辑 |
| functions/lease | 唯一服务端：席位租约 KV 读写，无业务规则之外的状态 | 不接触简历数据 |
| Rust 层 | 仅系统级能力：加密存储、对话框、设备指纹、SQL 插件宿主、更新器 | 不写业务逻辑 |

## 4. 角色与授权体系

### 4.1 角色定义

| 角色 | 进入方式 | 能力 |
|---|---|---|
| 内部开发者 `dev` | 开发者签名密钥（dev key，role=dev、默认 2 年、maxDevices=3） | 全部普通能力 + Prompt Studio（编辑/调试/导出签名包）+ 调试日志开关（查看原始 LLM 请求/响应） |
| 普通授权用户 `user` | 激活密钥（role=user、批次有效期、maxDevices=1 即一码一机） | 编辑器、AI 修订、评估、自有 API 配置 |

### 4.2 激活流程（离线验签 + 在线占席）

```
首启 → 激活向导 → 粘贴激活密钥
  → 本地 Ed25519 验签（公钥内置于应用）+ 校验 exp
  → POST /lease acquire { code, deviceIdHash }
     ├─ 席位空闲 → 返回租约 → 双证（license + lease）缓存至 SQLite → 进入应用
     └─ 失败 → 明确错误码：签名无效 / 已过期 / 已吊销 / 设备数满（附"解绑指引"）
```

### 4.3 双证设计：License（离线签名）+ Lease（在线租约）

| 证 | 载荷 | 签发/校验 | 作用 |
|---|---|---|---|
| License | `{ v, code, role, batchId, exp, maxDevices, iat }` | keygen 离线 Ed25519 签发；应用本地验签 | 证明密钥真实性与有效期，**密码学强制**，离线不可绕过 |
| Lease | `{ code, deviceIdHash, exp(=now+7d) }` | 租赁端点签发（HMAC）；应用每 72h `renew` 续期 | 证明"本机占有一个席位"，实现一码一机/设备数上限/及时吊销 |

- **宽限逻辑**：renew 时端点不可达 → 沿用现有租约继续使用，直到租约 TTL（7 天）耗尽 → 功能冻结（仅查看/导出）。离线最长可用期 = min(License.exp, Lease.exp)。
- **换机流程**：旧机"解绑此设备"（`release`）→ 新机 `acquire`；旧机丢失则等 7 天席位自动过期，或开发者经 `keygen unbind --code --all` 强制清席。
- **吊销时效**：renew 时校验 KV 吊销标记 → 最迟 7 天内生效（租约 TTL 即吊销上界）。

### 4.4 内部开发者密钥

- dev key 与用户 key 走同一签发管线，仅 `role` / 有效期 / `maxDevices` 不同；一人一码，泄露即经 `keygen revoke` 吊销。
- 前端据验签结果中的 `role` 门控 Prompt Studio 与调试视图，**无账号系统**。
- 签发私钥离线加密保存、绝不入仓；泄露需随应用版本更新轮换内嵌公钥（§15）。

### 4.5 授权租赁端点（唯一服务端，约 100 行）

```
KV 数据模型：code → { devices: [{ id: deviceIdHash, exp }], revoked: bool, maxN, batchId }

POST /lease        { action: 'acquire'|'renew'|'release', code, deviceIdHash }
  acquire：清理过期席位 → 未满则写入（exp = now + 7d）→ 返回 HMAC 租约；满则 'slots-full'
  renew：  本机在册且未吊销 → 延长 7d；被吊销/被清席 → 'revoked' | 'not-found'
  release：移除本机席位（应用内"解绑此设备"按钮）
POST /admin/{revoke|unbind}   Bearer 管理密钥（keygen 调用；吊销 / 清空席位）
```

- **隐私**：端点只见到 `code` 与 `deviceIdHash`（设备指纹的 SHA-256，不可逆推具体设备），无个人信息、无简历数据、无 IP 留存需求。
- **部署**：Cloudflare Workers + KV（免费额度 10 万读/日、1000 写/日；激活为一次性写 + 每设备每 72h 一次写，200 人批次月写入约 3000 次，量级安全）。国内直连实测不佳时整体平移至腾讯云函数 + TCJKV——代码是同一个 fetch handler，搬迁成本约半天。
- **已知取舍**（诚实记录）：KV 最终一致，极端并发下 `acquire` 可能瞬时超额一个席位（两人同秒抢同一席）；概率极低且后果有限（7 天后自动收敛），v1 接受，不引入 Durable Object。
- **防滥用**：按 IP Rate limit + 密钥格式前置本地校验（错码不出网）。

## 5. 编辑器核心设计

### 5.1 文档模型（Tiptap / ProseMirror 自定义节点）

```
resumeDoc
 └─ section[type: basic|education|experience|project|skill, title]
     ├─ field[label, value]                 # basic 区：姓名/电话/邮箱/链接…
     ├─ entry[org, role, start, end]        # education/experience/project 区条目
     │   └─ bullet[text]                    # 要点描述（AI 修订的主目标块）
     └─ skillGroup[name, items[]]           # skill 区
```

- 每个节点持有持久化 `data-block-id`（nanoid），生成后不变，作为：AI 修订定位、评估 finding 跳转、快照 diff 比对的锚点。
- 简历全文可序列化为 `ResumeDoc` JSON（zod Schema 定义于 shared），也是存储、快照、diff 的统一格式。

### 5.2 AI 块级修订交互（核心闭环）

```
光标位于/选中某 bullet 或 entry
  → Ctrl+K 或右键/悬浮菜单选择动作：改写 / 量化成果 / STAR 化 / 自定义指令
  → core 渲染提示词（垂类提示词包.revise + 块上下文 + 目标岗位可选输入）
  → LlmClient 流式请求（SSE）
  → 编辑区内该块下方实时渲染建议文本（幽灵预览）
  → 完成 → 转为内联 diff 视图（原文红 / 建议绿，按句对齐）
  → 用户：采纳（写入文档 + 自动快照） / 拒绝（清除） / 重新生成（换 temperature 重试）
```

- 修订会话状态（pending patch）不写入文档模型，以 ProseMirror decoration 叠加渲染，避免污染撤销栈；采纳时一次性事务提交。
- 每个 patch 记录 `{ blockId, action, promptVersion, model, originalText, suggestedText }`，随快照留存，供效果回溯。

### 5.3 快照与对比

- 触发：AI 采纳后自动 / 用户手动 / 评估前自动。
- 存储：完整 `ResumeDoc` JSON + 标签（"AI: 量化项目 X"）。
- 对比视图：按 `blockId` 对齐两版本，块级增/删/改三态高亮；支持一键回滚到任意快照。

### 5.4 导入与结构化

| 入口 | 实现 | 说明 |
|---|---|---|
| 粘贴文本 | Clipboard → 分段启发式 | 无 AI 依赖 |
| DOCX | WebView 内 mammoth → HTML → 白名单清洗 → 映射入 section 节点 | 纯前端，文件不出本机 |
| PDF | WebView 内 pdf.js `getTextContent()` → 纯文本 | 保排版取舍：仅取文本，不还原图形 |
| 结构化确认 | 文本 →（用户 Key）LLM 按 ResumeDoc Schema 归类 → 校验失败自动修复重试 1 次 → 用户在确认界面逐区核对 | AI 参与但数据不出用户自己的 API 链路 |

### 5.5 命令面板

Ctrl+K 全局唤起，动作注册表驱动：块级 AI 动作、全篇评估、新建分区、快照、导入、设置。命令注册表是插件式（`CommandRegistry`），垂类扩展（v2）可注册新动作。

## 6. AI 层设计

### 6.1 连接配置（普通用户自有 Key）

```ts
interface LlmProviderConfig {
  id: string                    // nanoid
  label: string                 // "我的 DeepSeek"
  preset?: 'deepseek' | 'qwen' | 'glm' | 'doubao' | 'custom'
  baseURL: string               // 如 https://api.deepseek.com/v1
  apiKeyRef: string             // 指向 stronghold 中的密钥条目，明文 Key 不落 SQLite
  model: string                 // 如 deepseek-chat
  headers?: Record<string, string>
}
```

- 预设内置四家（DeepSeek / 通义 Qwen 兼容模式 / 智谱 GLM / 火山方舟豆包）+ 自定义；"测试连接" 按钮发一条 1-token 请求验证。
- Key 通过 Tauri stronghold 插件加密存储，UI 回显仅尾 4 位；**Key 永不进入渲染进程持久层、永不上传**。
- 可配多个 Provider，按场景选择（如：修订用 deepseek-chat，评估用 glm-4.x）。

### 6.2 LlmClient（packages/core）

- 统一 OpenAI 兼容 `POST {baseURL}/chat/completions`，`stream: true`，`@microsoft/fetch-event-source` 处理 SSE（WebView 内 fetch，不经 Rust）。
- `sse-parser` 独立实现并单测：处理 `data:` 帧、`[DONE]`、`usage` 块、断流重连（指数退避，最多 2 次）。
- 场景路由：`ScenarioRouter` 将 `revise` / `evaluate` / `structure` 映射到用户选定的 Provider+model。
- 用量估算：状态栏显示本次会话累计 Token（中文约 1.5 字符≈1 token 的启发式 + 响应 usage 实值优先）。

### 6.3 结构化输出协议（评估场景）

- 提示词强制 JSON 输出 + `response_format: json_object`（不支持的服务商降级为提示词约束）。
- zod 严格校验；失败 → 携带错误信息发起修复重试（最多 1 次）→ 仍失败则给出友好错误并保留原始文本供开发者视图排查。
- temperature：评估 0.1，修订 0.7。

## 7. 评估体系

### 7.1 Rubric 协议（按垂类定义）

```ts
interface RubricDimension {
  id: string            // 'structure' | 'star' | 'quantify' | 'match' | 'keywords' | 'clarity'
  name: string          // '结构完整性'
  weight: number        // 0-1，总和为 1
  description: string   // 评分标准描述（注入提示词）
  promptHint?: string   // 垂类特化提示（如计算机类侧重技术栈表述）
}
```

v1 内置 `general` 通用垂类六维：结构完整性、经历描述质量（STAR）、量化与成果、岗位匹配度（可选输入目标 JD）、技能与关键词、表达清晰度。

### 7.2 评估流程与报告

```
ResumeDoc（+ 可选目标岗位/JD）
  → core/evaluator：按垂类提示词包.evaluate 合成提示词（整篇一次调用）
  → LLM 返回结构化 JSON → zod 校验
  → EvaluationReport：
     { verticalId, model, promptVersion, overall(加权总分),
       dimensions: [{ dimensionId, score(0-100), level(优/良/中/差),
                      findings: [{ blockId | null, severity(high|mid|low),
                                   message, suggestion }] }],
       summary }
  → UI：右侧诊断面板（问题清单按严重度排序，点击 → 编辑区滚动定位并高亮该块）
        雷达图（ECharts）+ 顶部总分
        "去修订"按钮 → 跳到首个 high finding 对应块并预选修订动作
```

- 报告持久化本地（SQLite），可与上一份报告对比总分/各维变化。
- `blockId` 定位由 LLM 在 finding 中引用文档提供的块索引（提示词中随简历附带 blockId 清单），跳转前做存在性校验，失效则置灰。

## 8. 提示词 SPI 与 Prompt Studio（核心扩展点）

### 8.1 SPI 定义（packages/shared）

```ts
interface VerticalPromptProvider {
  verticalId: string                  // 'general' | 'cs-engineering' | 未来任意
  displayName: string
  getPrompts(): PromptSet             // { revise, evaluate, structure } 各为带占位符模板
  getRubric(): RubricDimension[]      // 该垂类评估维度
}

interface PromptTemplate {
  template: string                    // {{resume_block}} {{jd}} {{action}} 等占位符
  version: number
  status: 'builtin' | 'remote-draft' | 'remote-published'
}
```

- 占位符渲染由 `core/prompt-renderer` 统一完成（mustache 风格），模板经 shared 的 zod Schema 校验后才可发布。
- **合并策略**：远端 `published` 包覆盖内置兜底包；离线时回落内置。兜底包随安装包发布，保证断网可用。

### 8.2 新增垂类的成本（关键设计目标）

新增一个垂类 = 向 `dist/prompts/<verticalId>/` 提交一个**签名包**文件（提示词 + rubric），**客户端零改动**——设置页自动出现该垂类选项。v2 的计算机垂类（代码编辑 + 题库）在此机制上追加 `capabilities` 声明与对应工作台组件（`VerticalCapability[]`，v1 仅在 SPI 注释中预留类型位，不实现 UI 插槽）。

### 8.3 Prompt Studio（内部开发者面板）

功能：
1. **包管理**：列出各垂类提示词包（内置/远端、版本、状态）。
2. **编辑器**：改 `revise` / `evaluate` / `structure` 模板与 rubric，实时 zod 校验 + 占位符补全。
3. **调试台**：选当前打开的简历（或内置样例简历）作为测试输入 → 用开发者自己的 Provider 配置发起真实调用 → 左右分栏看**完整合成提示词 / 原始响应 / 校验结果**——即"暴露调试不同专业岗位系统提示词接口"的落地形态。
4. **发布**：导出**签名包**（Studio 内调用签名能力，私钥在开发者本机配置）→ 推送至 `dist/prompts/<verticalId>/`；回滚 = 推回旧版本文件（目录保留最近 20 版）。客户端启动时 + 每 24h 拉取，验签通过后应用。

## 9. 数据模型

### 9.1 本地 SQLite（tauri-plugin-sql，`resume_ade.db`）

```sql
resumes(id TEXT PK, title, vertical_id, doc_json, -- ResumeDoc 序列化
        created_at, updated_at)
resume_snapshots(id TEXT PK, resume_id FK, doc_json, label,
                 trigger('ai-accept'|'manual'|'pre-eval'), created_at)
evaluations(id TEXT PK, resume_id FK, report_json, created_at)
settings(key TEXT PK, value_json)          -- 仅非敏感：UI 偏好、Provider 列表(含 apiKeyRef)、license+lease 缓存
ai_patch_log(id TEXT PK, resume_id, block_id, action, prompt_version,
             model, original_text, suggested_text, accepted, created_at)
```

### 9.2 GitHub 被动分发区（仓库内 `dist/`，零服务器）

```
dist/
├─ prompts/<verticalId>/pack.v{N}.json   # 签名提示词包（PromptPack + Ed25519 签名）
└─ prompts/manifest.json                  # { verticalId → { version, file, sha256 } }，指向当前生效版本
```

- 客户端仅做**只读拉取**：manifest → 指定包 → 验签 + sha256 校验后应用；任一失败回落内置包。
- 可达性：GitHub 直连（用户具备代理）为主，`cdn.jsdelivr.net/gh/<owner>/<repo>@<ref>/dist/...` 为免代理镜像备选，按超时自动切换。

### 9.3 keygen CLI（`tools/keygen`，开发者本机工具）

| 命令 | 作用 |
|---|---|
| `keygen init` | 生成 Ed25519 应用密钥对（公钥编译进应用，私钥加密离线保存） |
| `keygen issue --batch --role --days --max-devices --count --out` | 批量签发密钥 → CSV（code, key, batch, exp, maxDevices）交付客户 |
| `keygen pack --dir` | 校验并签名 Prompt Studio 导出的提示词包 → `dist/prompts/...` |
| `keygen revoke --code` / `keygen unbind --code [--all]` | 调租赁端点管理接口：吊销 / 清空设备席位 |

签名覆盖范围：激活密钥与提示词包共用同一应用密钥对（与 updater 的 minisign 密钥相互独立）。

## 10. 安全与隐私

| 项 | 措施 |
|---|---|
| API Key | stronghold 加密存储；UI 尾 4 位回显；仅 WebView 内存中直连厂商；不上传、不进日志 |
| 简历正文 | 仅本地 SQLite；AI 调用走用户自有 Key 的直连链路（用户已知悉并自担）；导入解析全部前端完成 |
| 授权 | 双证：Ed25519 离线验签（密码学强制有效期）+ 在线租约（一码一机、设备数上限、≤7 天吊销生效） |
| 租赁端点 | 只见 code + deviceIdHash（SHA-256 不可逆），无个人信息与简历数据；管理操作走 Bearer 密钥 + IP 限流 |
| 提示词包 | Ed25519 签名 + sha256 校验后才应用；发布经 zod 校验防注入破坏结构 |
| 传输 | 全链路 HTTPS；CSP 于 tauri.conf.json 收紧 `connect-src` 为所配厂商域名 + GitHub/jsDelivr 域名 + 租赁端点域名 |
| 签名私钥 | 离线加密双备份、绝不入仓；泄露的应对是随版本更新轮换内嵌公钥（§15） |
| 更新包 | minisign 签名，updater 校验后安装 |

## 11. 分发与自动更新

- **通道**：GitHub Releases（用户具备网络条件，已确认）。
- **同域复用**：提示词包（`dist/prompts/`）与 Releases 同仓分发——GitHub 仓库是更新与提示词的被动只读源；授权租约由独立的租赁端点承担（§4.5）。
- **流水线**：`.github/workflows/release.yml`，推 tag `v*` → tauri-action 构建 Windows NSIS x64 → minisign 签名 → 上传 Release + 生成 `latest.json`。
- **更新器**：tauri-plugin-updater，endpoint 指向 `https://github.com/<owner>/<repo>/releases/latest/download/latest.json`；启动时 + 每 24h 检查；用户确认后安装重启。
- **降级预案**：updater 失败时应用内"手动下载"按钮打开 Release 页。
- **版本策略**：semver；提示词包独立版本（pack version），与应用版本解耦。

## 12. Tauri 关键配置要点（实现期检查单）

1. `app.windows[].dragDropEnabled: false` —— 让 WebView 内 HTML5 拖拽（导入文件）正常工作；如需绝对路径再监听 `onDragDropEvent`（v1 不需要，File API 读字节足够）。
2. 插件：`stronghold`（Key）、`sql`（SQLite）、`updater`、`single-instance`、`dialog`。
3. 设备指纹：Rust 侧 `machine-uid` 取机器 GUID → SHA-256 哈希后仅以哈希出网（deviceIdHash）。
4. WebView2：仅 Windows 首发，渲染一致性风险锁定为单一引擎；中文 IME 在 Tiptap 的兼容性列入 M1 验收测试项。
5. CSP：`default-src 'self'`；`connect-src` 动态白名单（厂商 baseURL + github.com / raw.githubusercontent.com / cdn.jsdelivr.net + 租赁端点域名）。
6. Rust 代码量红线 < 300 行（不含 build 配置），超出即视为逻辑下沉违规，需回流 TS。
