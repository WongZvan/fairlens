# ADR：CI 门禁补齐（覆盖率 / Actions SHA pin / Playwright E2E）

> 日期：2026-11-21
> 状态：已实施
> 触发：外部审查（gpt-6sol）对 `dev=4b3d943` 提出三项差异，核查全部成立；另自查出 4 处同源漂移
> 相关：`docs/01` §3.1/§3.2/§14/§15 · `docs/02` ② · `.github/workflows/ci.yml` · `vitest.config.ts` · `playwright.config.ts`

## 1. 问题

| # | 问题 | 事实 |
|---|---|---|
| 1 | 覆盖率门禁缺失 | docs/01 §14 要求 shared/core/keygen/lease「单测 ≥80%（coverage 进 CI）」；实际 CI 只有 lint/typecheck/test/contract 四 job，无 coverage 配置、无 provider 依赖。326 测试全绿不等于覆盖率达标 |
| 2 | Actions 未 pin | `ci.yml` 用 `actions/checkout@v4` 等浮标签，违反 AGENTS.md §9；**且 m0.1 模块 MD 记着「actions 版本 pin」——文档与事实不符** |
| 3 | STATE 指针过期 | 写法把「当前分支」写成 squash 提交（`b4cc253`），而 HEAD 是回填提交（`4b3d943`）。STATE 写在提交里，自身必然再改变 HEAD——这是结构性循环，不是偶发笔误 |
| 4 | 术语漂移 | 全仓 20+ 处「CI 三门禁」，实际已 4 job、扩为 6 job |
| 5 | 占位无测试 | `functions/lease` 的 501 占位没有任何测试，却属于 §14 的覆盖范围 |

## 2. 决策

### 2.1 覆盖率：v8 provider，四项包，行/函数/分支逐包 ≥80%

- **指标**：行、函数、分支三项都设 80%。§14 原文只写「单测 ≥80%」；用户拍板取严格口径（三项都拦），避免「行覆盖达标但分支全是死路」。
- **逐包 glob 阈值**（`vitest.config.ts`），不用全局阈值：否则 shared 的 100% 会掩盖 keygen 的低覆盖。
- **范围**：`packages/shared`、`packages/core`、`tools/keygen`、`functions/lease`。`apps/desktop` 不纳入——规格未要求，且桌面行为由 E2E + 人工验收覆盖，单测覆盖率对 UI 层意义有限。
- **provider 选 v8 而非 istanbul**：v8 原生、无需额外转译插桩、与 vite/vitest 同栈；istanbul 的语句级更精确但对本项目没有增量价值。
- **基线实测**（2026-11-21）：core 96.27 / shared 100 / keygen 93.84 / lease 100（行）；分支 92.79 / 88.46 / 95.65 / 100。门槛留有余量，但不过度宽松。

### 2.2 keygen CLI 抽 `runCli` 以便测试

原 `cli.ts` 是顶层过程式脚本（37 行，含 `process.exit`），单测无法触达 → keygen 覆盖率卡在 48%。抽为 `run.ts`：

```ts
export function runCli(argv: string[], deps: CliDeps): number
```

`deps` 注入 `keysDir`/`exists`/`mkdir`/`writeFile`/`generate`/`log`/`error`；`cli.ts` 只留 4 行入口装配。**行为逐条不变**（子命令校验、`--env` 必填、私钥已存在拒写、输出文案），`package.json` 的 `keygen` 脚本不动。新增 7 条测试覆盖全部拒绝路径与 dev/prod 成功路径。

**否决**：从覆盖率统计里排除 `cli.ts`——账面达标但真实未测，属于自欺；spawn 子进程跑 CLI——需要额外环境变量注入点、慢且易受环境影响。

### 2.3 lease 占位纳入门禁

`functions/*` 加入 `vitest.test.projects`，为 501 占位补 1 条测试（状态码 + `invalid-request` + content-type）。m2.1 实现落地后自动继续受管，不需要再改配置。

### 2.4 Actions 固定到提交 SHA

- 三个 action 全部改 40 位 SHA，行尾注释保留版本号（checkout v4.4.0 / pnpm-action-setup v4.4.0 / setup-node v4.4.0）。
- **升级流程**：单独提交改 SHA + 注释 → 观察一次 CI 绿 → 再合并；不随功能改动顺手升级。
- 顶层加 `permissions: contents: read`（最小权限）。
- **m0.1 模块 MD 的「actions 版本 pin」不实记录一并修正**，并在偏离节注明是外部审查发现。

### 2.5 CI 六 job

`lint` / `typecheck` / `test` / `coverage` / `contract-zero-drift` / `e2e`。

**coverage 独立成 job 而不并入 test**：失败原因一眼可辨（是测试挂了还是覆盖率掉了），也便于分支保护单独要求。代价是多一次 install + 测试，约 1 分钟。

### 2.6 Playwright：浏览器模式关键路径

- 配置 `playwright.config.ts`：单 chromium，`webServer` 起 `pnpm --filter @fairlens/desktop dev`，CI `retries: 1` + `trace: on-first-retry`。
- 用例 `e2e/smoke.spec.ts`：激活 → 进入编辑器 → 编辑要点 → 切模板 → 保存。断言只用结构化钩子（`.fl-host[data-template]`、`.toast`），不做像素比对。
- **边界（重要）**：只跑浏览器模式（内存持久层）。SQLite 落盘、窗口三键、圆角、PDF 导出、IME 真机都不在 E2E 范围，仍走 `acceptance/M1.md` 人工验收。E2E 绿**不能**替代真窗验收。
- **否决 tauri-driver/WebDriver**：Windows 支持与稳定性不足，维护成本高于收益；真窗自动化不是当前瓶颈。

### 2.7 附带修复：根 `pnpm build` 在 Windows 上失效

`package.json` 的 `build` 用单引号包 filter（`--filter './packages/*'`）。pnpm 在 Windows 用 `cmd.exe` 执行脚本时单引号不是引号字符 → filter 收到字面量 `'./packages/*'` → **No projects matched the filters**，构建静默变空操作（CI 在 Linux 不受影响，所以一直没暴露）。改为双引号（sh 与 cmd 都正确去掉引号），本地 `pnpm build` 恢复。

**教训**：跨平台 npm scripts 只用双引号；「CI 绿」不能证明本地脚本可用。

## 3. STATE 指针根治

不再追着 hash 跑，改为写清三层并固化约定：

```
HEAD=4b3d943（回填提交）→ 最近 squash=b4cc253 → 代码基线=cceb793
```

> STATE 写在提交里，所以 HEAD 恒比表内所写的 hash 多一个回填提交；核对以 `git log -1` 为准。

## 4. 验证

- `pnpm test:coverage`：四个包行/函数/分支全部 ≥80（334 测试，43 文件）。
- `pnpm test` / `lint` / `typecheck` / `contract:check` / `build` 全绿。
- `pnpm e2e`：1 passed（8.1s）。
- `ci.yml` YAML 可解析；六 job；全部 `uses` 为 40 位 SHA。
